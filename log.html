Research Log

Everything that happened, in order, including what broke. Written so someone with no prior context can read start to finish and understand the whole process: what was decided, what was tried, what failed, and why the current state is what it is.

2026-08-14

Project scoped done

The JDEI proposal was read and its scope locked: a fixed camera watches Cal Poly Food Pantry shelves, an on-device model estimates occupancy and flags low stock, all inference stays on the device. Public shelf-detection datasets were surveyed and a two-stage data strategy was chosen (pretrain on dense retail imagery, fine-tune on empty-shelf sets), and the detector architecture was chosen (YOLO11n: small enough for the Jetson, accurate enough for the task). Three camera options were priced for the PI.

2026-08-14 to 15

The deployment site, measured from video done

No site visit had happened yet, so a promotional video the pantry had already published was analyzed frame by frame: 250 frames, cross-referenced against known object sizes (brick coursing, can dimensions, a commercial reach-in fridge of known make) to reconstruct a dimensioned floor plan and shelf elevation. This is the Building 27 Pantry Survey: room geometry, camera coverage math, power locations, and an inventory of what the camera would actually need to recognize.

2026-08-15

Baseline model trained on Colab done

Six public empty-shelf datasets were pooled (4,860 training images, one class: gap) and YOLO11n was fine-tuned on a free Colab GPU. The first run was interrupted twice by Colab reclaiming the VM mid-training. The fix: point training output at a mounted Google Drive folder so every epoch's checkpoint survives a disconnect, and make the script auto-resume from the last checkpoint instead of restarting. After that fix, disconnects cost at most one epoch instead of the whole run.

Result: mAP50 0.898, mAP50-95 0.639 on the retail validation split.

2026-08-15

EXP-001: the retail model meets the real pantry done

The trained model was run on real pantry photos it had never seen. Its single most confident detection anywhere (0.70) was the painted fruit decoration on the wall above the shelves. It also flagged empty counter space and, in one frame, a shopper's hair, while missing shelves that were genuinely empty. The pattern: the model had learned "dark flat region," not "empty region inside a shelf." Full write-up and images: Phase Zero Report, EXP-001.

2026-08-15

EXP-002: 15 labeled frames from the site done

Fifteen frames from the pantry's own video were hand-labeled (7 gap boxes, 8 negatives including the decor wall) and used to fine-tune the model for two minutes on a laptop CPU. Every false positive observed in EXP-001 disappeared, and the model began detecting gap types it had missed before, including a freezer shelf it had never seen labeled. This became the deployment model, v2. Before and after images: Phase Zero Report, EXP-002.

2026-08-15

On-device monitoring loop built and tested done

The full runtime pipeline was written: a guard that refuses to report a number when the camera view looks wrong (lights off, camera bumped or blocked) rather than guessing, per-shelf occupancy from the gap detections, a filter that requires a shelf to read low for a sustained period before it is reported (a single odd frame should not trigger an alert), and a plain-text summary for staff. It was tested against video frames standing in for a camera: fed frames from different viewpoints, it correctly refused 29 of 30 as "camera moved"; fed two frames of the same fully-stocked view, it read all shelves correctly and produced a clean summary. Diagram and test output: Building 27 Survey, Sheet 7.

"Great progress! I have not done a deep dive into the write up from your site. But did look at the overall organization, your thought process and plan for collecting the training data. It looks good to me." (reply received the same day)

The PI agreed to order the camera and asked what else to include in that order; a small hardware list was sent back (NVMe SSD, microSD card, an active USB extension cable sized from the room measurements, and a wall mount). The PI is separately locating the pantry's admin contact for installation permissions. 2026-08-15

EXP-004: does dense-retail pretraining help done

With the Kaggle recipe working, the originally planned comparison ran: pretrain on SKU-110K (a dense retail-shelf dataset, 11,743 images) before the gap fine-tune, versus fine-tuning directly. This was pre-registered before the run: the decision rule for adopting the pretrained model was fixed in writing in advance, so the result could not be interpreted to fit a preference.

Pretraining won on the benchmark, and also produced fewer false positives on real pantry photos with zero pantry-specific data, meaning the improvement was not just curve-fitting to the validation set. Per the pre-registered rule, it replaced the previous approach. Re-applying the same 15-frame pantry fine-tune on top of this stronger base produced v3, the current deployment model, which detects the hardest real-world test case (a bare shelf) at meaningfully higher confidence than v2 did (0.43 versus 0.29).

2026-08-15

Casting a wider net for training data done

A search was run across public dataset platforms for additional empty-shelf imagery and, separately, for any real food-pantry photos (the closest match to the actual deployment domain). Four sizable new detection datasets were found and downloaded. One risk surfaced immediately: several of the new sources and the sources already pooled appeared to be different exported versions of the same underlying photographs by the same authors, which would silently duplicate images between the training set and the validation set and make later results look artificially good.

Every image was fingerprinted (a perceptual hash, robust to resizing and re-compression) and checked against the frozen validation and test sets before being added. 809 duplicates were caught and dropped, including 56 that would have leaked into validation.

The pantry-domain search came back thin: the closest match was a small (~220 image) academic pantry photo set, labeled for identifying items rather than empty shelves, of limited direct use but a useful data point that pantry-specific imagery is genuinely scarce in public datasets.

2026-08-15

EXP-006: does the model's percentage match reality done

Every result so far used mAP, a score for bounding boxes. But the system's real output is a percentage on a staff summary ("shelf 3 is 30% full"), so a separate question matters: how far off is that percentage? A held-out dataset reserved since the first day of planning answers it: 180 shelf images from three sources where every gap pixel was hand-traced by researchers, giving exact ground-truth gap fractions to compare against.

v1: baseline14.6 points0.166

An error of ~12 occupancy points is compatible with the digest's design, which reports coarse levels (EMPTY / LOW / OK, each spanning 25 to 40 points) rather than precise percentages, with a persistence filter absorbing flicker near level boundaries.

Near-miss worth recording: the first run of this evaluation silently paired only 59 of the 180 images. One source names its files differently (image 100jpg.jpg for mask 100.tiff) and the pairing code missed the pattern, dropping two-thirds of the evaluation without any error message. On the truncated set the model ranking was inverted: v3 looked worst. Only checking the image count against the expected total exposed it. The conclusion an evaluation produces can depend entirely on data that silently went missing; every eval table now gets its n verified first.

2026-08-15

Setback: more data made the model much worse setback

The retrain on the expanded 12,433-image pool finished with 0.659 mAP50, a 26-point collapse from the 0.920 baseline. Adding 2.6 times the training data produced a dramatically worse model. Diagnosis took about twenty minutes and found real label poisoning:

  • One new source shipped with two annotation classes. Its second class was genuine empty-slot labels (6,119 boxes), but its first class was 130,733 boxes drawn around products. The merge step collapsed all classes to "gap", so the training set taught the model that products are gaps. That single source injected more wrong labels than the rest of the pool has correct ones.
  • A second source turned out to be industrial pallet-rack imagery with boxes drawn over bays that contain stock: wrong domain and doubtful labels.

Rendering sample images with their merged boxes made both problems obvious in seconds; the lesson is that this rendering step belongs before training, not after. Fix: the poisoned source was re-added keeping only its genuine empty-slot class (verified visually: boxes now sit on real gaps), the pallet-rack source was dropped entirely, and the cleaned 11,624-image pool was re-uploaded. The retrain is running again. The bar is unchanged: 0.920 on the same frozen validation split.

2026-08-16

EXP-005 concluded: quality beats quantity done

The retrain on the cleaned 11,624-image pool finished at 0.902 mAP50: cleaning recovered 24 of the 26 points the poisoned run lost, but the expanded pool still came in below the smaller curated pool's 0.920. The full battery agreed. Occupancy error: 12.3 points versus 11.8. And on the most important real-world check, the candidate model missed the bare case shelves that the current model detects. The current model (v3) stays.

Correction, 2026-10-22: the validation mAP50 row scores each pool's base model before the pantry fine-tune. This table originally labeled that column "v3", but 0.920 is the base model's score. The deployed v3 scores 0.29 on the same retail data (see the 2026-10-22 entry). The occupancy and bare-shelf rows are after the fine-tune.

The finding: doubling the training data produced a strictly worse model, even with the label poisoning removed. The added sources' differing annotation styles and heavy augmentation diluted the target distribution rather than reinforcing it. This closes the public-data avenue with a measured answer: the remaining way to improve the model is real imagery from the pantry itself, which is exactly what the first weeks of the semester will collect. A negative result, but a decision-shaping one: effort now goes where the data is scarce and valuable instead of where it is plentiful and cheap.

2026-08-16

The data question, asked harder and closed done

A challenge worth recording: was the search for training data actually thorough? A second sweep answered it properly. Thirteen previously unprobed dataset leads were checked by API; four were downloaded and rendered for inspection, and three were rejected on sight (one "empty space" dataset turned out to be photographs of bolts on a parts tray). Every non-Roboflow platform - Kaggle, HuggingFace, Zenodo, Dataverse, Figshare, IEEE DataPort, GitHub, synthetic-data pipelines - was swept and documented empty for this task. Two ideal academic datasets exist but are locked behind author permission. The search is now exhausted in the strong sense: every thread named, every dead end recorded.

The sweep also surfaced one real hypothesis: maybe EXP-005 failed because the added data was bulk and sloppy, and carefully verified additions would still help. EXP-007 tested exactly that, with the rule fixed in advance: the winning pool plus only inspection-passed additions, including researcher-grade labels derived from hand-traced masks. Result: 0.892, below both the original pool (0.920) and the cleaned bulk pool (0.902). Three experiments now form one line: every public-data addition, careful or not, made the model worse on the fixed benchmark.

One honest caveat, stated in the record: the benchmark's validation images come from the same sources as the original pool, which structurally favors it. What these experiments prove is that public data is spent as a lever. What actually improves the deployed system will be decided by imagery from the pantry itself, which is precisely what the first weeks of the semester collect. The current model (v3) enters the semester as the final Phase 0 model.

2026-08-16

EXP-008: manufacturing pantry data done

With public data closed, one lever remained reachable before any camera exists: synthesizing pantry-domain training images by compositing verified gap crops from the labeled frames into other pantry frames. The first attempt failed its own inspection gate twice before training even started (one donor crop contained a volunteer's arm; another was freezer interior that looked alien pasted on wood shelving), which is the inspection process working as designed.

Two training rounds against the pre-registered bar: the synthetic-augmented model doubled its confidence on the hardest real gap (0.43 to 0.86) with near-clean false-positive behavior, but its occupancy calibration regressed slightly both rounds (11.9 vs 10.9 points), so by the rule it was not adopted. The mechanistic read: pasted crops teach what pantry gaps look like but their arbitrary sizes distort how much area the model attributes to them.

The takeaway is a prediction: if artificial pantry data moves recognition this much, real on-site imagery, with correct sizes in correct contexts, should capture the gain without the calibration cost. That is now the strongest quantitative argument for the data collection planned in the first weeks of the semester. The deployment model remains v3; the week-2 hardware bring-up is now scripted end to end (flash, build engine, calibrate, run as an auto-restarting service).

2026-08-16

A third data sweep, and a citation retracted done

An observation about the deployment site opened one last search angle: the pantry buys its core stock in bulk, a few consistent brands restocked repeatedly. A small fixed catalog makes per-item recognition tractable in a way open-ended retail recognition is not. So a third sweep asked a new question of the public data: not "are there empty-shelf boxes" but "are there brand-item datasets worth training on." Thirty-five queries against the dataset platform's search API returned 493 distinct projects, each screened by class list and sample imagery.

The answer is again no, and again useful. Every brand-item pantry dataset found is tabletop close-up photography, a hand holding a soup can at arm's length, which does not transfer to a fixed camera viewing a shelf wall. One 893-image candidate whose class names suggested fill-level annotation was downloaded in full and turned out to be supermarket egg-carton displays, unrelated to its own title. But two small student projects demonstrated the recipe that matters: working closed-set detection of five to seven fixed products from a few hundred self-collected images. That is precisely the shape of the on-site option this fall, applied to the pantry's own bulk catalog, and it is now recorded as the validated path should item-level detail prove wanted.

The sweep also forced a correction. An earlier literature pass had recorded a pantry-domain labeling dataset attributed to a university lab. Verification across the dataset platform's search, its API, and the open web found no trace of it, so the citation was retracted from the project record; the datasets that anchor the novelty claim were re-verified live the same day and stand. A record that catches its own unverifiable citation is doing its job: every claim in this log is meant to survive exactly this kind of audit.

2026-08-17

Dress rehearsal: four defects the benchmarks could not see done

Before the hardware arrives, the full monitoring loop was run against a live camera in daylight rather than the simulated frames used until now. The model was never the point of the exercise. The point was everything around it: opening a camera, waiting for it to expose correctly, pacing readings, and writing the message staff actually read. Four defects surfaced, none of which existed in simulation, and all four were fixed.

The most serious one is worth stating plainly. The out-of-distribution guard did its job perfectly: pointed at the wrong scene, it refused every single frame and recorded why. But the daily staff digest rendered that state as "All 0 shelves OK. Nothing needs attention." A monitor that had measured absolutely nothing was reporting good news. In deployment, a bumped camera or a drifted calibration would leave pantry staff reassured while the system sat blind. The digest now says "NO READINGS YET" and explains what to check. Blindness has to be louder than an empty shelf.

The other three were quieter but would each have stalled the hardware bring-up. The interval setting that is supposed to take one reading per minute was never applied, so the loop ran the detector on every incoming frame, roughly a thousandfold more work than intended and a continuous load on a device meant to idle between readings. The camera was never released after use, which leaves the device locked and makes the next start hang forever, precisely the calibrate-then-start sequence the deployment script uses. And calibration captured its reference from the very first frame, before automatic exposure had settled, recording a brightness of 35 for a scene that stabilizes at 143 a second later; that single early frame then caused every subsequent reading to be rejected as out of range.

The lesson generalizes past this project. Accuracy metrics measure the model; they say nothing about the seams between a camera and a model, and those seams are where an unattended system actually fails. For a deployment whose entire premise is running quietly for months without supervision, a monitor that reports its own blindness as normal is a more dangerous defect than any accuracy shortfall, and no benchmark would ever have caught it.

2026-08-17

Writing the report, and auditing its own numbers done

With the hardware a week away and site access gated on a partner introduction, the highest value work left was the deliverable itself. Every section of the final report that does not depend on fall data is now written as prose rather than outline: motivation and the measurement caveats around campus food insecurity statistics, related work and the corrected novelty position, the justice-centered design commitments, the system design, the site characterization method, the full arc of data experiments, and the evaluation protocol with its results. What remains genuinely requires the deployment to exist.

Writing it surfaced something worth recording. A systematic sweep of every underlying page found the same quantities stated slightly differently in different places, because pages were written weeks apart as results arrived. The occupancy error figure appeared without the confidence threshold it depends on, and that threshold had itself moved. The pantry adaptation set was described once by its labelled size and once by its training split. Dataset growth was described with multipliers that referenced different baselines. None of these were errors of fact, and every one of them was a chance to publish two numbers that contradict each other.

They are now fixed to one convention each in a single reference page, which the report, the poster, and this site all defer to. Two stale lines in the experiment records were corrected at the source. The exercise also forced a more honest statement of one claim: the promise that raw images are never stored is enforced in code for the deployed monitor, but it cannot cover the training-image collection that necessarily retains labelled frames. The report now says so explicitly rather than letting a clean sentence do work the architecture does not do.

2026-09-04 to 2026-09-12

Reaching the pantry, and agreeing the terms done

The partner channel was slower than planned. The PI's first outreach to the pantry went about two weeks without a reply, and a walk-in visit was cancelled before it happened. The reply came in the second week of the semester. A scheduling conflict with a class meant the PI met the director who oversees the pantry alone and toured the space.

The director's first concern was privacy, and the terms that came out of the conversation are stricter than the original design. Frames are captured every 30 minutes. If a person is in frame, the system waits until they leave rather than skipping the reading. No frame containing a person is ever retained, and blurring faces was ruled out as a substitute. Training images come from a bounded two to three week acquisition window, with sample images reviewed by the pantry before the IRB submission, and the team has access during closed hours.

Two working assumptions were corrected as a result. Face blurring was removed from the IRB mitigation plan, since the partner had explicitly ruled it out. The assumption that each cubby holds one product was dropped: under heavy traffic, shelf assignments shift through the day. The terms also exposed a design tension. A strict wait-for-an-empty-frame rule in a client-choice pantry, where people browse all day, may push most readings into low-traffic and closed hours. That tension is still open and shapes the capture schedule.

2026-09-16

Building the person gate done

The new terms made a person detector a hard requirement, and the gap model was never trained to see people. The gate runs a stock COCO-pretrained detector alongside the gap model and allows a reading only on a frame with nobody in it, waiting up to 20 seconds for a clear shot before trying again at the next cycle. It was tested on real pantry footage and on four scripted scenarios: a person leaving the frame, a timeout, the video source ending mid-wait, and a frame that is already clear.

The tests found a real bug. An early throttle design could consume more frames than a short test source contained, then report the source as exhausted before ever reaching a clear frame. On a live camera that would have looked like a monitor that silently stops taking readings. What the tests did not establish is the gate's miss rate under occlusion, side angles, and low light. That number matters beyond engineering, because the gate's reliability determines which tier of IRB review the project needs.

2026-09-21

Hardware in hand, and a first site visit done

The Jetson Orin Nano developer kit and a 500 GB NVMe drive were picked up, and bring-up started. Power was confirmed. First boot is waiting on a DisplayPort cable, a keyboard and mouse, and an SD card reader. The kit has no HDMI port, and the SD-card flash path from macOS avoids needing an Ubuntu host.

The same day, the director who oversees the pantry authorized the install on two conditions: nothing permanently damaging, and a camera that is not too big. The first rules out anchoring into the brick. The second favors a compact USB webcam over the larger CSI sensor with an add-on lens. The director also asked for on-site signage explaining the camera, which is drafted but deliberately not posted until the person gate's miss rate is measured, because the sign makes a technical claim.

2026-10-01

Characterizing the person gate, while three blockers stood still setback

The first visit was an authorization meeting, not a technical survey: no measurements and no calibration frame. For ten days afterward, three blockers did not move: the camera order, a second technical visit, and the Jetson peripherals. No single cause was to blame. The visit was waiting on a promised day-to-day contact, and nobody followed up. The fix was procedural: a direct follow-up to the director and a dated plan for each blocker.

The person gate did move. Run against all 250 frames of existing pantry footage, the nano detector scored zero on a partially occluded person at every confidence threshold. The next size up, YOLO11s, caught that person and seven more cases with no regressions anywhere in the set, so it became the default. The caveat stands: this is promotional video, well lit and mostly frontal. The real miss rate has to be measured on footage from the mounted camera.

The follow-up worked. The director named the pantry coordinator as the project's day-to-day contact, and the coordinator replied with visit windows right away. The technical visit was set for the following week. 2026-10-21

Technical visit, and the room rebuilt at full scale done

The second pantry visit was a tape-measure visit. The cubby wall is nine columns on a 24 in pitch over a 216 in counter, two openings per column, each 22.8 in wide and 9.85 in tall. The planned mount is the top of a 72 in storage cabinet across the aisle, 76 in from the cubby face and 73 in from the run's left end. A duplex outlet with one free receptacle sits behind the milk crates beside that cabinet, so the Jetson can share the cabinet top with the camera.

The measurements also graded the August video photogrammetry. Horizontal quantities held: column count, run length, and opening width all fell inside the estimated ranges. Vertical ones did not. The opening height was overstated by about 35 percent and the camera standoff by over a foot, consistent with brick coursing being the weak vertical reference. That result goes into the report's methods section as a validation of the pre-visit survey, error and all.

From these numbers the room is now a 1:1 model, the Building 27 Pantry Model, with the webcam's view simulated from the mount and each cubby region projected into the frame. Unmeasured values are tagged as estimates, and the page sweeps them to show which ones could change a decision. The geometry answers several questions the report needs. One camera covers columns 2 to 5, eight of eighteen openings, at about 18 px per inch, and that holds across the full range of the unmeasured dimensions, so the prototype scope can be fixed now. For items stacked close to the shelf above, the camera sees only the front 5.5 in of the 13 in low row, which means a one-deep facade and a full cubby look the same there. Occupancy will be reported as visible front-face fill, and that limit will be stated. A 3 in can is 54 px in the full frame but 27 px if the whole frame is resized to the model's 960 px input, so each cubby is cropped before inference. A shopper anywhere in a 68 in stretch of the aisle is in frame and delays that reading.

2026-10-22

The Jetson comes up, and the model is checked on the device done

The Orin Nano now runs JetPack 6.2.1 from its 500 GB NVMe drive. It boots without the microSD card, which was used once to bring the system up and is now kept as a rescue disk. Its firmware was already on the JetPack 6 line, so no older release had to be flashed first. The software environment installed with two dependency failures, both fixed and written back into the setup script. A generic ONNX Runtime package was silently replacing the GPU build, and an automatic dependency update pulled in a NumPy version that crashed the model export.

The deployed model was compiled into a TensorRT engine on the device, at half precision (FP16) and the 960 px input size. On the 156-image retail test split, the engine and the original weights scored the same: mAP50 0.3054 for both, mAP50-95 0.1735 versus 0.1737. Inference takes 20.9 ms per frame, 31 percent faster than full precision. Converting for the edge cost no measurable accuracy.

The same runs turned up a mislabeled number in this log. The 0.920 mAP50 quoted since August is the pretrained base model's score, and it reproduces on the device at 0.915 (validation) and 0.927 (test). The deployed model, after its 15-frame pantry fine-tune, scores 0.24 and 0.29 on the same retail data. The fine-tune traded retail box accuracy for better gap area, since v3 still has the lowest occupancy error on the pixel-mask benchmark, 11.8 points versus the base's 14.2. The report will quote both numbers, and the pantry evaluation will score both models, so the deployed model is picked on pantry data rather than on retail data.

The complete monitoring loop then ran on the device against the 194 frames of pantry footage: person gate, detector, cubby regions, shelf state, and the staff digest. It finished cleanly, and a filesystem check afterward found that no image file had been written anywhere. Only numbers were. The module drew 4.6 W at the median and 7.4 W at peak. Two privacy settings were changed before any camera is attached. The vision library's usage analytics are off, and the USB audio driver is blocked, because the webcam has a built-in microphone and the project has committed to never enabling one.

One gap surfaced in the plan. Everything written for review so far describes the monitoring mode, where frames are never kept. Measuring accuracy on real pantry shelves needs a bounded collection of shelf-only frames that are kept for labeling. That collection now goes to the IRB inquiry before any frame is retained.
